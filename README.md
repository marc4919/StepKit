# StepKit (iOS)

StepKit turns a goal into a plan of small, dated steps ("Kits") and helps the
person follow it. Plans are generated by the StepKit server, which also syncs
data across devices and checks subscriptions. The app is native SwiftUI with
no third-party dependencies.

The backend lives in a separate repository (`StepKitServer`, Vapor 4 + PostgreSQL).

## Requirements

- Xcode 26 or newer (the project uses file-system synchronized groups and
  string catalogs).
- iOS 26.0 deployment target. The app target is iPhone-only
  (`TARGETED_DEVICE_FAMILY = 1`).
- A running StepKit server for anything beyond the offline design fixtures
  (see [Configuration](#configuration-and-environments)).

Apple frameworks used: SwiftUI, SwiftData, StoreKit 2, AuthenticationServices
(Sign in with Apple), TipKit, UserNotifications, os (Logger).

## Build and run

Open `StepKit.xcodeproj` in Xcode, pick the `StepKit` scheme and an iPhone
simulator, and run. From the command line:

```bash
xcodebuild build -project StepKit.xcodeproj -scheme StepKit -configuration Debug \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

## Tests

Unit tests (no server needed):

```bash
xcodebuild test -project StepKit.xcodeproj -scheme StepKit \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -only-testing:StepKitTests
```

UI tests (`StepKitUITests`):

- `ManualKitUITests` and `KitAssistantUITests` run on the offline design
  fixtures and need no server.
- `StepKitUITests` is an end-to-end journey against a real server started with
  E2E sign-in enabled (`ENABLE_E2E_AUTH=true`, Debug server build, development
  environment). The base URL defaults to `http://127.0.0.1:8080` and can be
  changed with the `STEPKIT_E2E_BASE_URL` environment variable of the test
  runner (`TEST_RUNNER_STEPKIT_E2E_BASE_URL=… xcodebuild test …`). The journey
  writes to that server's database: point it at a disposable one.

## Configuration and environments

| Build | Info.plist | `StepKitAPIBaseURL` |
| --- | --- | --- |
| Debug | `Configuration/StepKit-Debug-Info.plist` | a local development server |
| Release | `Configuration/StepKit-Release-Info.plist` | the production server (HTTPS) |

`AppEnvironment` validates the URL at launch: Release requires HTTPS, rejects
local hosts and ignores overrides.

Debug-only launch arguments:

| Argument | Effect |
| --- | --- |
| `-StepKitAPIBaseURL <origin>` | Use another server for this launch |
| `-StepKitDesignFixtures <scenario>` | Offline demo data for a screen (`kits`, `empty`, `kit`, `step`, `create`, `assistant`, `calendar`, `profile`, `paywall`, `signIn`, …; see `DesignFixtures.swift`) |
| `-StepKitCanvas <W>x<H>` | Draw the app inside a frame of that size (layout review) |
| `-StepKitE2EAccount account-a\|account-b` | Sign in through the server's E2E route instead of Sign in with Apple |
| `-StepKitE2EResetLocalState` | Clear local data before the E2E sign-in |
| `-StepKitE2ESuppressNotifications` | Do not request notification permission |
| `-StepKitShowTips` | Reset TipKit and show every tip right away (design fixtures hide tips) |

Subscriptions can be tested locally with `Configuration/StepKit.storekit`,
which the `StepKit` scheme already uses. Server-side receipt validation happens
on the server only.

## Localization

Spanish is the source language; English is the second localization. Strings
live in `StepKit/Localizable.xcstrings` and `StepKit/Subscription.xcstrings`.
Write new user-facing text in Spanish with `String(localized:)` or SwiftUI text
literals and add the English translation in the catalog.

## Logging

Use `AppLog` (`Core/Logging/AppLog.swift`), a thin wrapper over `os.Logger`
with one category per area. Never log user content, tokens or identifiers that
could identify a person.

## Secrets

The repository holds no secrets. Signing uses the Apple developer team set in
the project; server URLs are the only environment-specific values and live in
the Info.plists above.
